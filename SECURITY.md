# Security Policy

## Supported Versions

We currently support the latest version of create-psychic v3. Our goal is to avoid breaking changes within major versions, facilitating incorporating security patches by updating to the latest minor and patch version within a supported major version.

## Reporting a Vulnerability

To report a vulnerability, please contact us at [psychic-security@rvohealth.com](mailto:psychic-security@rvohealth.com). Once the vulnerability is verified, a patch will be provided. Once the patch is provided, a new version will be published closing the vulnerability. Private contact will resume between the reporter and the code maintainers until the vulnerability is resolved.

## Supply-chain hardening

This package is developed and published with defenses against install-time supply-chain attacks (the Shai-Hulud class of npm worm, which runs from a dependency's `postinstall` and/or publishes a compromised version for maintainers to install before it is noticed):

- **Dependency build scripts are blocked by default.** pnpm 10+ does not run dependency lifecycle scripts; `pnpm-workspace.yaml` keeps a deliberately minimal `allowBuilds` allowlist (only the few packages that genuinely need to build). Every entry re-opens script execution, so additions require a clear reason.
- **Release-age cooldown.** `pnpm-workspace.yaml` sets `minimumReleaseAge: 4320` (3 days; pnpm 11+ ignores release-age keys in `.npmrc`), so freshly-published dependency versions — the window in which most worm-injected releases are caught and unpublished — are not installed. Three days stays under the critical-CVE patch SLA, so routine patching never needs a bypass.
- **The cooldown exclude list is `@rvoh/*`-only.** Only our own first-party packages are exempt from the cooldown. pnpm enforces `minimumReleaseAge` from `pnpm-workspace.yaml` on every install: it resolves no version younger than the cooldown, and it checks every `pnpm-lock.yaml` entry against it, so CI's `pnpm install --frozen-lockfile` fails on an entry younger than 3 days. The `@rvoh/*` entry in `minimumReleaseAgeExclude` is the only standing bypass. Changes to `pnpm-workspace.yaml`, `.npmrc`, any pnpmfile, or the workflow files are reviewed like any other code change. For an urgent third-party patch, add a one-off exclude for that exact version (`'<package>@<version>'`) and remove it once that version is 3 days old; removing it sooner fails every install, CI's included.
- **Registry pinning.** `.npmrc` pins the npm registry so installs cannot be redirected to a malicious mirror.

Apps generated by create-psychic ship their own `SECURITY.md` describing the equivalent hardening configured for the generated app (per-package-manager script blocking, cooldown, registry pinning, Node floor, and optional hardened CI).

## Publishing posture

Releases are published by GitHub Actions. Publishing a GitHub Release runs [`.github/workflows/release.yml`](.github/workflows/release.yml), which publishes that version to npm with [trusted publishing](https://docs.npmjs.com/trusted-publishers/): npm exchanges the workflow run's GitHub OIDC token for a short-lived publish token, so the workflow uses no stored npm token. [RELEASING.md](RELEASING.md) has the procedure. Every version from 3.5.7 on was published this way: for each, the registry lists GitHub Actions as the publisher, with a trusted-publisher record and a provenance attestation. Earlier versions have none of these.

The workflow:

- runs only when a release is published, so a draft release publishes nothing;
- fails before it builds if the release tag is not `v` followed by the `version` in `package.json`;
- installs dependencies with `pnpm install --frozen-lockfile`, under the cooldown above and with no dependency cache;
- publishes each version with a signed [provenance attestation](https://docs.npmjs.com/generating-provenance-statements/) recording the repository, the workflow file, the tag and the commit it was built from. npm shows it on the version's page, and `npm audit signatures` verifies the attestations of installed packages. As npm notes, provenance shows where and how a package was built; it does not guarantee that the package has no malicious code.

The tradeoff: no maintainer's npm two-factor prompt gates a publish from CI, and npm keeps a standing trust relationship with this repository's release workflow. What guards a release is GitHub access: anyone with Write access to the repository can publish a GitHub Release, and the release job uses no GitHub environment, so no deployment approval stands between a published release and npm. Any code the release job runs, including the dependencies its build runs, could publish with the job's OIDC permission. Trusted publishing also does not stop npm from accepting a publish made directly by one of the package's npm owners.
