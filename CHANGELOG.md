## 3.8.0

- The generated app's four sign-in helpers (`resolveCurrentUser`, `resolveCurrentAdminUser`, `resolveCurrentInternalUser` and `resolveWebsocketUser`) now treat a credential they cannot open — missing, empty, forged, garbled or encrypted under a different key — as signed out: the HTTP helpers return no user, so the request gets a 401, and the websocket helper returns `null`. Previously Dream's `DecryptionError` escaped as a 500, or, in the websocket helper, as an unhandled rejection that exited the websocket process. The helpers log nothing when they reject a token, as Psychic's `getCookie` has logged nothing for a cookie it cannot open since 3.16.0. Any other error, including a token that decrypts but holds malformed contents, still propagates. The admin and internal helpers also get the missing-token guard `resolveCurrentUser` got in 3.5.3, and now read `adminUserId`/`internalUserId`, the keys their test tokens are minted with, so a regular user's token no longer signs in there. Test-token minting in `spec/unit/helpers/authentication.ts` now encrypts objects instead of JSON strings, so the helpers no longer `JSON.parse` the decrypted value (a failed parse there could carry the decrypted plaintext into the error log). The admin and internal minters also cast `primaryKeyValue()` to `string`, clearing the two `no-unsafe-assignment` errors a generated app's lint reported there.
- The generated request logger now masks secrets in the request body, the query string, the request headers and the path's route parameters, not only in top-level body fields with an exact listed name. A new dependency-free `conf/system/redactForLog.ts`, used by `conf/system/requestLogger.ts`, replaces with `[FILTERED]`, keeping the key, any body or query-string value whose key contains a `bodyBlocklist` name, ignoring case, at any depth and inside arrays, and the value of any logged header whose name contains one. So `{ user: { token } }`, `[{ token }]`, `accessToken`, `?token=` and headers such as `x-auth-token`, `proxy-authorization` and `x-api-secret` no longer reach the log, while harmless names such as `tokenCount` are masked too. The `referer` header's query string is masked by the same rule, so a `referer` ending in `?token=abc` is logged ending in `?token=[FILTERED]`. A header whose whole name is listed in `headerBlocklist` is still left out, as before. `SENSITIVE_FIELDS` and `headerBlocklist` are unchanged, so a header whose name contains none of the listed names, such as `x-api-key`, is still logged as sent. Matched top-level fields are now masked instead of dropped, arrays stay arrays instead of becoming `{ "0": … }`, and the body the controller sees is never modified. Anything nested more than ten levels deep is logged as `[TRUNCATED]`, which stops a deeply nested body of about 10 KB from making the logger throw and the request 500 after the controller ran. In the logged URL's path, the value of a route parameter whose name contains a `bodyBlocklist` name is masked by the same rule, so a request to a route such as `/password-resets/:token` is logged as `/password-resets/[FILTERED]`, and a parameter named like `tokenId` is masked too. Only the segment the matched route (`ctx.routerPath`) binds such a parameter to is masked, so a request to `/v1/api-tokens/42/usages/1420`, matched by `/v1/api-tokens/:apiTokenId/usages/:id` (psychic's `resources('usages')` nested under `resources('api-tokens')`), is logged as `/v1/api-tokens/[FILTERED]/usages/1420`, and a parameter bound inside a segment (`confirm-:token`) masks that whole segment. Where the route does not line up with the path segment by segment (a splat such as `*path`, an optional `{…}` group, two parameters in one segment such as `:a-:b`, or a path that splits differently, such as an absolute URL), or the value is not in a segment the route binds it to, every segment that equals or contains the value is masked instead, so a splat's value masks each segment it spans, as does any other segment that happens to contain it (a `tokenId` of `1` there also masks `v1`). A path that matches no route (a 404), a request with a method its route does not take (a 405, or an `OPTIONS` request), a request that middleware mounted after the logger answers before the router runs (such as a rate limiter's 429) and the `referer`'s path are logged as received, with only their query string masked; middleware mounted ahead of the logger keeps the requests it answers out of the log, either with `psy.use(…)` in `conf/app.ts` above the hook that mounts the logger, which keeps it after CORS, or with `psy.use('before-middleware', …)`, which also works from an initializer but runs before CORS, so a browser sees a CORS failure instead of the 429. A comment beside the logged URL in `conf/system/requestLogger.ts` now says so, and says that for a link such as an emailed sign-in or reset link the URL fragment, which browsers never send to the server, is still the safest place for a token.
- The generated websocket initializer (`conf/initializers/websockets.ts`) now signs sockets in from a single `ws:connect` hook instead of a `connection` listener added in a `ws:start` hook. psychic-websockets contains a throw from `ws:connect`: it logs the error, fires `ws:error` and disconnects only that socket. A throw from the old listener (a database or Redis error, or the development "replace before production" throw in `resolveWebsocketUser`) became an unhandled rejection, and `ws.ts` exited the whole websocket process. A socket with no user is still disconnected. The `allowRequest` comment no longer suggests token checks there, where a throw is not contained either, and the comment promising an automatic `/ops/connection-success` message, which nothing sends, is gone.
- The generated `conf/dream.ts` comment now says to set `DB_NO_SSL=1`, not `DB_NO_SSL=true`, to turn TLS off. Dream's `Env#boolean` accepts only `1`, so `true` left verified TLS on and pg failed with "server does not support SSL". The code, the generated env files and generated CI already used `1`.
- A newly generated app's `lint` no longer fails on `conf/system/allowedCorsOrigins.ts`. Since 3.7.7 moved the template to ESLint 10, whose recommended rules make `preserve-caught-error` an error, the error that file throws for a malformed `CORS_HOSTS` failed lint because it did not carry the JSON parse error as its `cause`. It now does, and the message is unchanged. In an existing app, pass `{ cause: err }` as the second argument to that `new Error(...)`. `src/app/controllers/MaybeAuthedController.ts` also failed that lint, with `no-unused-vars` on its `resolveCurrentUser` import: the only line using it, `this.currentUser = await resolveCurrentUser(this)`, is one of the "uncomment after creating User model" lines. The import now sits under that same marker, beside the `User` import handled the same way, so uncomment it together with that line. In an existing app that has not created its `User` model yet, comment that import out the same way.
- Fourteen template files that the generator copies unchanged, among them `src/main.ts`, `src/ws.ts`, `src/worker.ts`, `conf/initializers/workers.ts` and `resolveCurrentInternalUser.ts`, are now formatted with the generated app's own Prettier settings, and the generator now writes `package.json` with a final newline and `docker-compose.yml` with single-quoted strings and a final newline, so the `prettier . --check` in a newly generated app's `lint` script no longer flags them. Only formatting changed, except that the instruction comment in `resolveCurrentInternalUser.ts` now says to replace "the signature above", because Prettier wraps that signature over three lines. The app's `.prettierignore` now also lists the cloned psychic-skill (`.agents/skills/psychic-skill` and `.claude/skills/psychic-skill`), so in an API-only app generated with the skill, where the skill sits inside the app, that check no longer flags the skill's Markdown files and the app's `format` script no longer rewrites them: the skill keeps its upstream formatting, which its updater restores. In an existing app generated with the skill, add those two lines to `.prettierignore` (in an app with a client, the one at the root). What the generators write is not always Prettier-formatted, such as the serializer and the migration that `psy g:model` (from `@rvoh/dream`) writes; the app's regular `format` script formats it.
- Existing apps: these are all changes to the generated template, and upgrading create-psychic does not change an app it already generated. To pick them up, copy them into your app: the four sign-in helpers together with the new token minting in `spec/unit/helpers/authentication.ts` (the helpers no longer re-parse the decrypted value, so a token minted the old way, as a JSON string, now fails loudly: the helper throws a fixed-text error saying the token minting and the helper disagree, so the request gets a 500 and a websocket connection is disconnected); `conf/system/redactForLog.ts` plus the updated `conf/system/requestLogger.ts` (logs now show a matched value as `[FILTERED]` instead of dropping the field, mask query-string values, secret-named route parameters in the path, matching header values and the `referer`'s query string, and truncate beyond ten levels); the `ws:connect` hook in `conf/initializers/websockets.ts`, in place of the `ws:start` sign-in listener; and the `DB_NO_SSL=1` comment in `conf/dream.ts`. The sign-in helpers need `@rvoh/dream` 2.11.1 or later (the first release that exports the decryption errors they import from `@rvoh/dream/errors`), and the `ws:connect` containment needs `@rvoh/psychic-websockets` 3.4.0 or later (the template's `ws:error` hook needs 3.5.0); upgrade those first.
- Scaffolding a pnpm or yarn app no longer fails on Node 25 and later, which stopped bundling `corepack`. The generator ran `corepack enable` unconditionally before installing, so it exited with `corepack: command not found` even when `pnpm` or `yarn` was already installed. It now uses `pnpm`/`yarn` as-is when `pnpm --version` or `yarn --version` succeeds and falls back to `corepack enable` only when it does not. A version manager's shim that resolves the name but cannot run the package manager, as nodenv's does when the active Node has none, does not count as installed. This covers the api install and a yarn client's setup; the generated app's own CI workflow and `Dockerfile.dev` still run `corepack enable`.
- A new pnpm app's `package.json` now declares `engines.pnpm` `>=10.19.0`. Because `new` now uses an installed pnpm as-is instead of letting corepack replace it, a pnpm 10.15 or older on the PATH would install the app without its 3-day cooldown, and say nothing. pnpm refuses to install under a root `engines.pnpm` it does not satisfy, so such a pnpm now stops `new`, and every later install, with `ERR_PNPM_UNSUPPORTED_ENGINE` and the version it needs. 10.19.0 is the first pnpm that applies every cooldown setting the app's `pnpm-workspace.yaml` writes: `minimumReleaseAge` arrived in 10.16.0, pattern excludes such as `'@rvoh/*'` in 10.17.0 and exact-version excludes such as `'express@4.22.3'` in 10.19.0. pnpm 10.16 treats `'@rvoh/*'` as a package name, so it fails a new app's install with `No matching version found` while an `@rvoh` floor is under 3 days old. Each pnpm client app (`client/`, `admin/` or `internal/`) is a pnpm project of its own, which the api's `engines` does not reach, so its `package.json` now declares the same `engines.pnpm`, and a later `pnpm install`, `pnpm add` or `pnpm update` there with an older pnpm stops with the same error instead of ignoring the client's cooldown. Existing pnpm apps: add `"pnpm": ">=10.19.0"` to `engines` in `package.json`, the api's and each pnpm client's.
- `new` now accepts an app name only when it is a letter followed by letters, digits, dashes (`-`) or underscores (`_`). Any other name, such as `my app`, `my.app`, `3d-shop` or one containing a shell metacharacter, is refused before `new` prompts for anything or writes a file, with a message naming the allowed characters and exit code 1. The name used to be pasted unquoted into the shell commands that install dependencies, set up a client app and run git, so a name such as `app;touch pwned` ran the extra command. Those commands also contained the current directory's full path, so `new` failed in a folder whose path has a space in it even when the name was valid. Each of those commands now runs in its folder through the child process's working directory, and neither the name nor a path appears in the command text. Capitalized names such as `MyApp` still work: the folder and the `package.json` `name` keep the name as typed (pnpm, npm, yarn and bun install, run and audit a private package with a capitalized name without a warning), and database names are derived as before (`MyApp` gives `my_app_development`). `init` is unchanged; its name never reaches a shell command.
- A pnpm or yarn client app (`client/`, `admin/` or `internal/`) now gets the api's 3-day supply-chain cooldown. A pnpm client's `pnpm-workspace.yaml`, which held only `strictDepBuilds: false`, now also sets `minimumReleaseAge: 4320`. A pnpm client is its own pnpm project, so the api's cooldown never applied to it. A yarn client's `.yarnrc.yml` now sets `npmMinimalAgeGate: 4320`; it set no gate before, so Yarn applied its built-in one-day default. A pnpm Next.js client now also widens create-next-app's exact `next` and `eslint-config-next` pins to their major range (`^<major>.0.0`), as a yarn Next.js client already did, so the cooldown can fall back to an older release instead of failing the install while the pinned release is under three days old. A pnpm or yarn Nuxt client likewise widens the `nuxt`, `vue` and `vue-router` floors that `nuxi init`'s minimal template sets, because that template raises its `nuxt` floor to each new release within a day or two of it shipping.
- The api's `pnpm-workspace.yaml`, both the template's and the one `init` writes, now exempts `@rvoh` packages from the cooldown with one `'@rvoh/*'` entry instead of naming six packages, so an `@rvoh` package the app adds later is exempt too. Its comment and the generated `SECURITY.md` now say that pnpm 11 and later read the cooldown only from `pnpm-workspace.yaml` and ignore release-age keys in `.npmrc`, and that each pnpm client carries its own copy. The `SECURITY.md` runbook now says to keep a one-off pnpm exclude, or a lowered cooldown, until that version is 3 days old: pnpm checks every lockfile entry against the cooldown on each install, `--frozen-lockfile` included, so restoring the setting sooner fails every install. Existing apps: add `minimumReleaseAge: 4320` to each pnpm client's `pnpm-workspace.yaml`, or `npmMinimalAgeGate: 4320` to each yarn client's `.yarnrc.yml`; the six named `@rvoh` excludes keep working.
- A new app's `puppeteer` is now `~25.16.0` instead of `~25.10.0`, so a new pnpm app's `pnpm audit --audit-level moderate` is clean again. Puppeteer 25.10.0 pins `chromium-bidi` 17.0.2, which depends on zod 3, and every zod release before 4.6.6 is affected by a high-severity advisory (GHSA-mrhx-c7xc-m3w5: validating oversized constrained collections can exhaust memory) that no 3.x release fixes. Puppeteer 25.13.0 and later use a `chromium-bidi` that takes zod ^4.6.5. Feature specs now run on Firefox 158.0.1 instead of 155.0, which each new app downloads with `puppeteer browsers install firefox` as before; puppeteer's launch options are unchanged. `init` already installed the latest puppeteer. Existing apps: set `puppeteer` to `~25.16.0` in `package.json`, reinstall, and install the matching Firefox (`pnpm puppeteer browsers install firefox`, or your package manager's equivalent).
- A new app's `@rvoh/dream`, `@rvoh/psychic` and `@rvoh/psychic-websockets` floors are now `^2.40.1`, `^3.18.0` and `^3.5.3` instead of `^2.30.1`, `^3.13.0` and `^3.5.0`, and the app no longer installs `kysely-codegen`. Since 2.37.0, Dream's `sync` writes `types/db.ts` itself instead of running kysely-codegen, so nothing in a new app used it. Psychic 3.18.0 requires Dream 2.40.0 or later. In psychic-websockets 3.5.3, `Ws.register` skips a socket that has already disconnected, so a socket that disconnects while the template's `ws:connect` hook awaits `resolveWebsocketUser` is no longer registered. pnpm and yarn apps already installed these releases, because their cooldowns exempt `@rvoh` packages, and so did bun apps, which have no cooldown. npm's cooldown has no per-package exemption, so a new npm app's install fails until the newest of these releases (psychic 3.18.0, published 2026-10-26) is 3 days old. `init` already installed the latest `@rvoh` releases, and no longer installs `kysely-codegen`. Existing apps: once on `@rvoh/dream` 2.37.0 or later, remove `kysely-codegen` from `devDependencies` and reinstall.
- A new app's `build` and `build:spec` scripts now run `tsc` once instead of twice, and the app no longer installs `tsc-alias`. Since 3.1.0, the step after the compile, meant to run tsc-alias, ran `tsc` a second time with the same settings, so tsc-alias was installed but never ran, and the built output is unchanged. npm, yarn and pnpm apps now call `tsc` by name, as their scripts already call `tsx` and `vitest`, instead of `./node_modules/.bin/tsc`, `yarn tsc` or `pnpm tsc`; Bun apps still compile with `bunx tsc` and Deno apps with `deno run -A npm:typescript/tsc`. `init` no longer installs `tsc-alias` either; nothing it writes ran it. Existing apps generated by 3.1.0 or later: delete the second `tsc -p …` step from `build` and `build:spec` and remove `tsc-alias` from `devDependencies`, unless the app runs tsc-alias itself, for example from a Dockerfile. An app generated before 3.1.0 calls `tsc-alias` in those scripts to rewrite its `@` imports in the built output, so keep it there.
- A new app now declares its import style once, in `conf/app.ts`, and `conf/dream.ts` declares none of it. `psy.set('importExtension', '.js')` sets the suffix, and `psy.set('importAliasPrefix', '#')` the alias prefix (the `#` of `#models/User.js`), of the import paths that `psy g:model`, `psy g:resource` and the other generators write, and a comment above the two lines says to set them there only. Psychic 3.18.0 passes both settings to Dream, whose generators read them, and throws at boot when `conf/dream.ts` sets a different value that is not Dream's default. A new app used to declare neither, so its generators wrote Dream 2's default `@` prefix. `init` now writes both lines into `conf/app.ts` for a Psychic app, where it used to write a `.ts` or `none` extension into both `conf/app.ts` and `conf/dream.ts`, and into `conf/dream.ts` for a `--dream-only` app, which has no `conf/app.ts`. Existing apps: delete an `app.set('importExtension', …)` line from `conf/dream.ts` that `conf/app.ts` repeats. An app whose imports still use `@` needs no new line while it is on Dream 2, whose default prefix is `@`. - A new app's files now import each other through Node's `#` subpath imports instead of `@` path aliases, as in `#conf/AppEnv.js` and `#models/User.js`, the form `psy g:model`, `psy g:resource` and the other generators now write. `package.json` gains an `imports` map, the one place a Node or Bun app defines these names, and each name points at a source folder with no extension (`"#models/*": "./src/app/models/*"`), so tsx, Vitest, tsc and Bun load the `.ts` file behind a `.js` import. `build` and `build:spec` now copy `package.json` into `dist/` after the compile, which makes `dist/` a package of its own, so in the built app the same names load the compiled files. As a result `node dist/src/main.js`, `psy:js` and `console:js` start: since 3.1.0 they failed with `ERR_MODULE_NOT_FOUND` at the first `@` import, which `tsc` leaves as written. `tsconfig.build.json` no longer has `paths` and compiles as `module: nodenext` instead of `Node16`, and both Vite configs drop their `resolve.alias`. `fspec:js` now runs Vitest from the app folder with `--root ./dist` instead of `cd ./dist`, because `dist/package.json` repeats the app's scripts: from inside `dist/`, the package manager would run a client app's `client:fspec` there, and its `../client` would point inside the api folder. A Bun app now declares `engines.bun` `>=1.4.0`, which the generated CI's setup-bun reads; Bun 1.3 does not load the `.ts` file behind a `#` import and stops at the first one. A Deno app's `deno.json` import map now lists the `#` names. The production Dockerfile example in the generated `SECURITY.md` now starts `dist/src/main.js`, the app's entry point, instead of `dist/src/index.js`, which does not exist. `init` copies the template files with their `#` imports and adds `#` names, instead of `@` names, to the host's tsconfig `paths`, which tsc, tsx and Next.js read; it adds no `imports` map to the host's `package.json`. Among them, `#src/types/*` and `#src/utils/*` point at the types and utils paths `init` copies those folders to, so the copied files' `#src/types/...` and `#src/utils/...` imports also resolve when those paths are not `src/types` and `src/utils`, and `#src/*` still points at `./src/*`. Existing apps keep working with their `@` aliases. To switch one: add the `imports` map to `package.json`; change every `'@conf/`, `'@controllers/`, `'@models/`, `'@serializers/`, `'@services/`, `'@spec/` and `'@src/` import to the same name with `#`; remove `paths` and `moduleResolution` from `tsconfig.build.json` and set `module` to `nodenext`; remove `resolve.alias`, and the `srcPath` import only it used, from both Vite configs; add `&& cp package.json dist/package.json` after the `tsc` step of `build` and `build:spec`; in an app with a client, change `fspec:js` to run `vitest --root ./dist --config ./spec/features/vite.config.js` instead of `cd ./dist && vitest --config ./spec/features/vite.config.js`; add `psy.set('importAliasPrefix', '#')` to `conf/app.ts`, so the generators write `#` imports too; and, in a Bun app, use Bun 1.4.0 or later.
- Existing Bun apps: use Bun 1.4.0 or later, the floor a new Bun app's `engines.bun` now declares, even if the app keeps its `@` aliases and so still starts on Bun 1.3. On Bun 1.3, once a client has connected, the websocket process ignores SIGTERM and keeps running until a second signal arrives: after a WebSocket upgrade, Bun 1.3's `node:http` server never calls back from `close()`, so socket.io's `io.close()`, which `Cable.stop()` awaits before `ws.ts` exits, never finishes. The template does not change.
- A new app with websockets no longer has a `ws:fspec` script, which ran the websocket server under test as a separate process and which nothing in the app ran. Its feature specs now start the websocket server themselves, inside the spec worker, as psychic-websockets' own test app does since 3.5.4: `spec/features/setup/hooks.ts` starts a `Cable` in `beforeAll`, after the api server, on `WS_PORT` or, when that is unset, on 8889, the port `src/ws.ts` uses under test. Until now that `Cable` was a commented-out block, added in 3.7.6, for a developer to uncomment when a spec needed a live `Ws.emit` push, and it always used port 8889. A separate process does not work, for two reasons: Dream gives each spec worker its own test database, so that process can read a different one and miss the rows a spec creates; and in test, websockets use the in-process adapter, so that process never receives a `Ws.emit` made in the spec worker. Comments in `hooks.ts` and in the generated `spec/features/setup/globalSetup.ts` say so. `afterAll` stops the `Cable` before the api server, so a failing `server.stop()` cannot leave the websocket port taken when the next spec file starts its own, and stops the api server in a `finally`, so a throw from `cable.stop()` cannot leave the api server's port taken. A `WS_PORT` exported in the shell also reaches `ws:dev`, so while a `ws:dev` started from that shell runs, the feature specs cannot start their `Cable`; the comment in `hooks.ts` says so. A new app without websockets, which has no `@rvoh/psychic-websockets`, now gets a `hooks.ts` with no `Cable` lines at all, where it used to get the commented-out block. Existing apps: delete `ws:fspec` from `package.json`. If `globalSetup.ts` launches the websocket server with `PsychicDevtools.launchDevServer`, remove that launch and its `stopDevServer`. If the app uses websockets, start a `Cable` in `hooks.ts` as a new app's does: import `Cable` from `@rvoh/psychic-websockets` and `AppEnv` from `#conf/AppEnv.js` (or the app's own path to `conf/AppEnv`), add `let cable: Cable`, put `cable = new Cable()` and `await cable.start(AppEnv.integer('WS_PORT', { optional: true }) || 8889)` in `beforeAll`, after the api server starts, and in `afterAll` replace `await server.stop()` with `try { await cable?.stop() } finally { await server.stop() }`. Uncommenting the 3.7.6 block gives the same, apart from the port and the `finally`. An app without websockets can delete that commented-out block.
- A new app now has a locale check, `spec/unit/conf/locales.spec.ts`, which runs with the other unit specs. It passes the app's locales and base locale to Psychic's `I18nProvider.localeDifferences` and fails, listing one line per difference, when a locale in `src/conf/locales` is missing a key the base locale has, has a key the base locale lacks, has a string where the base locale has nested translations or the reverse, or uses different `%{…}` placeholders. Without it, a missing translation shows up only in front of a user, as the base locale's text, which Psychic falls back to for a key the requested locale lacks. `src/utils/i18n.ts` now exports the base locale as `BASE_LOCALE` (`'en'`), and both its `I18nProvider.provide` call and the spec read it, so changing the base locale there changes what the spec compares against. A new app has only `en`, so the spec passes until a second locale is added. `init` does not write the spec, because it writes none of the unit-spec setup (`spec/unit/vite.config.ts` and its setup hooks) a spec runs under, though the `i18n.ts` it copies into a Psychic app exports `BASE_LOCALE` too. Existing apps (`localeDifferences` needs `@rvoh/psychic` 3.16.0 or later): export `BASE_LOCALE` from `src/utils/i18n.ts`, pass it to `provide`, and copy in `spec/unit/conf/locales.spec.ts`, writing its `#conf/` and `#src/` imports as `@conf/` and `@src/` in an app still on `@` aliases.
- A new app's `ApplicationController` now has a protected `locale` getter. It returns the locale from `supportedLocales()` in `src/utils/i18n.ts` that the request's `Accept-Language` header prefers, or the new `DEFAULT_LOCALE` beside it (`'en-US'`, typed as one of the supported locales) when the header is missing, is `*` or accepts none of them. The default is named rather than taken from the list's order, because Dream writes a locale enum's `LocalesEnumValues` in alphabetical order: an app supporting `en-US` and `de-DE` that returned that list would otherwise answer such requests in German. The getter hands Koa `DEFAULT_LOCALE` first, since Koa itself answers a request with no header, or with `*`, with the first locale it is given. It calls Koa's `ctx.acceptsLanguages`, so Koa's `accepts` and `negotiator` packages do the negotiation, not template code: they rank languages by q-value, rule out one marked `q=0`, ignore case and match a bare `es` to `es-ES`, so with `es-ES` supported, the browser headers `es-ES,es;q=0.9`, `es-MX,es;q=0.9` and `fr;q=1, es;q=0.5` all get `es-ES`. Its type is the list's element type, so it can be passed straight to the app's `i18n` function as well as to `serializerPassthrough` and `Model.passthrough`. ## 3.5.2

- Pre-declare the pnpm `allowBuilds` map (`esbuild: false`, `msgpackr-extract: false`, `puppeteer: false`) in the generated `api/pnpm-workspace.yaml`. pnpm 11 rewrites `pnpm-workspace.yaml` on every non-interactive install, appending any build-script dependency it hasn't been told about as the invalid placeholder `<pkg>: set this to true or false` ([pnpm/pnpm#11574](https://github.com/pnpm/pnpm/issues/11574)) — so a freshly-generated app's checked-in workspace file was getting mutated the first time the user ran `pnpm install`. Listing the three build-script deps the boilerplate ships keeps the file untouched on install. All three are pinned to `false` (blocked), so the security posture is unchanged: none of them needs its build script to run (esbuild/msgpackr-extract ship prebuilt binaries; puppeteer's browser is installed by an explicit step). Applies to both the `new` (boilerplate) and `init` (dependency installer) flows; `SECURITY.md` is updated to match. A new transitive build-script dep will still surface as a placeholder on first install — set it to `false` (or `true` only if it genuinely must build).

## 3.5.0

- **Node/Deno/Bun runtime support.** New `runtime` prompt (and `--runtime` flag) that, for `deno`/`bun`, subsumes the package-manager prompt — each is its own toolchain. Per-runtime generation: `bun install`/`deno install`, lockfiles, run/tsc commands, `deno.json` (import map + sloppy-imports + nodeModulesDir) / `bunfig.toml` config (emitted instead of `.nvmrc`), rewritten package.json scripts (so app code runs on the chosen runtime, not the Node `.bin` shims), and runtime-aware hardened GitHub Actions CI (SHA-pinned `setup-bun`/`setup-deno`). Requires `@rvoh/dream` ≥ 2.12.0 and `@rvoh/psychic` ≥ 3.5.0 in generated apps. Node + pnpm remain the defaults.
- Prompt options now show each runtime's / package manager's install-time supply-chain posture (lifecycle-script blocking + release-age cooldown). Deno/Bun are NOT positioned as more secure than pnpm: runtime permission flags are process-wide (they can't isolate dependency code from app code), so egress hardening belongs at the infrastructure layer (see the generated `SECURITY.md`), not the runtime.
- Boilerplate: `node:os` import prefix in `workers.ts` (Deno rejects bare builtin specifiers); `dotenv` bumped to `^17.2.3` to align with the `@rvoh` packages so Deno resolves a single `@rvoh/dream` copy.
- Generation now runs package binaries / scaffolders with the selected package manager instead of always falling back to `npx`. The puppeteer-browser install uses `pnpm`/`yarn`/`bunx`/`deno` as appropriate (DRY'd behind a shared `execCmdForPackageManager` helper, replacing the two duplicated switch/ternary copies in `CiWorkflowBuilder` and `installApiDependencies`); `create-next-app` now uses `pnpm create next-app` / `yarn create next-app` (matching the existing `create vite` handling); and the `nuxi` (Nuxt) scaffolder uses `pnpm dlx` / `yarn dlx` via a shared `dlxCmdForPackageManager` helper. Previously all three used `npx` for pnpm/yarn apps. `npm` and `bun`/`deno` behavior is unchanged.
- Boilerplate `api/src/conf/initializers/websockets.ts` now selects the websockets transport adapter per environment: `test` uses the in-process adapter (no Redis — hermetic unit specs, with real in-process delivery to feature specs for broadcasts emitted within the websocket-server process; cross-process fan-out still needs Redis, as in production), while `development`/`production` keep the Redis adapter. The Redis connection is now configured only outside of `test` (gated behind `!AppEnv.isTest`), so generated apps no longer open a Redis socket during `test`. Requires `@rvoh/psychic-websockets` ≥ 3.2.0 (the release that introduces the adapter seam); the boilerplate dependency floor is raised accordingly.
- Boilerplate `api/src/conf/initializers/websockets.ts` now documents the two configurable connection limits (commented, since both keep their prior defaults): `maxConnectionsPerUser` caps how many sockets a single user may register at once (registering past the cap evicts that user's oldest socket — a per-user resource bound), and `maxConnectionTtl` sets the garbage-collection TTL on the socket-id registry key (a backstop for ungraceful disconnects, not the live socket's lifetime). Requires `@rvoh/psychic-websockets` ≥ 3.3.0; the boilerplate dependency floor is raised accordingly.
- Bun-targeted generated apps now set `trustedDependencies: []` so **no** dependency runs install/postinstall scripts. Bun's "default-deny" is not actually deny-all — it ships a built-in allowlist of popular packages (puppeteer included), so without this it would run puppeteer's Chrome-download postinstall. The empty list matches the block-all posture of pnpm (`strictDepBuilds`) / npm (`ignore-scripts`) / yarn; the browser is still installed explicitly via `bunx puppeteer browsers install firefox`. CI (`pr-checks.yml`) installs Bun (`oven-sh/setup-bun`) so the bun-runtime generation specs run.
- The boilerplate's `@rvoh/*` dependency floors track their latest published versions, so generated apps require the newest Dream/Psychic (e.g. the `psychic-spec-helpers` flakiness fix). Caveat: npm has no per-package release-age cooldown exclude ([npm/rfcs#895](https://github.com/npm/rfcs/issues/895)), unlike pnpm/yarn, so a freshly-published `@rvoh` floor can't be `npm install`ed until it clears the 3-day cooldown. Rather than weaken the cooldown (its Shai-Hulud-class protection) or pin `@rvoh` below latest, create-psychic's own npm app-generation specs are temporarily skipped (`npmAppGenerationDisabled.ts`); pnpm/yarn/bun coverage is unaffected.

## 3.4.2

- Boilerplate `api/spec/features/setup/hooks.ts` now calls `resetBrowserState()` (from `@rvoh/psychic-spec-helpers` ≥ 3.1.0) in `afterEach`. The feature-spec browser is shared across spec files, so without per-spec cleanup `localStorage`/cookies leak between specs (incomplete isolation) and an in-flight request can keep a pooled DB client checked out across `server.stop()`. `resetBrowserState()` clears storage + cookies and navigates to `about:blank`, fixing both. The connection-lifecycle robustness itself is handled upstream in `@rvoh/dream` (bounded pool drain); this keeps per-spec teardown fast, clean, and properly isolated.
- Boilerplate `api/src/conf/dream.ts` now sets sensible pg connection defaults on the primary/replica credentials via the `pg:` key added in `@rvoh/dream` 2.11.2: `connectionTimeoutMillis` (default `5000`, override via `DB_CONNECTION_TIMEOUT_MS`) so an exhausted pool / DB stall fails fast instead of hanging forever (pg default is `0` = wait forever); `application_name` (from `APP_NAME`) so connections aren't anonymous in `pg_stat_activity` / server logs during incident response; and `keepAlive: true` so dead connections behind a load balancer / NAT are detected. `statement_timeout` / `query_timeout` / `idle_in_transaction_session_timeout` are intentionally left unset with an inline comment pointing to the Postgres-role approach (a blanket app-wide value would kill long migrations/reports). Generated apps get these defaults; the `@rvoh/dream` library itself stays backward compatible (nothing defaulted there). The boilerplate `AppEnv` allowlist gains `DB_CONNECTION_TIMEOUT_MS` (integer) and `APP_NAME` (string) so generated apps typecheck, and the boilerplate dependency floors are raised to `@rvoh/dream ^2.11.2` and `@rvoh/psychic-spec-helpers ^3.1.0` (the versions that ship the `pg:` passthrough and `resetBrowserState`) so a resolved older version can't silently drop these.
